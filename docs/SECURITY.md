# Security Model

This document describes the cryptographic design, key lifecycle, threat model, and known limitations of Vault.

---

## Cryptographic Primitives

### Key Derivation — Argon2id

Vault uses **Argon2id** (via the `argon2` crate) to derive a 256-bit encryption key from the user's master password and a random salt.

| Property | Value |
|----------|-------|
| Algorithm | Argon2id (hybrid of Argon2i and Argon2d), version 0x13 |
| Output length | 32 bytes (256 bits) |
| Salt length | 16 bytes (128 bits), generated by `OsRng` |
| Parameters | 128 MiB, 3 passes, 1 lane (`KdfParams::DEFAULT`): about 0.3 s per attempt on a recent laptop |

Argon2id is **memory-hard**, meaning brute-force attacks are significantly more expensive than with bcrypt or PBKDF2. The salt is unique per vault, and both the salt and the parameters are stored in the vault's header, so the default cost can be raised later without breaking existing vaults.

Vaults written before format v1 used the `argon2` crate's defaults at the time (19 MiB, 2 passes, about 10× cheaper to attack). When such a vault, or any vault keyed below the current cost, is unlocked, it is rewritten right away with a fresh salt and a key at the current cost. Costs are never lowered this way.

### Symmetric Encryption — AES-256-GCM

Vault encrypts the serialized entries map using **AES-256-GCM** (via the `aes-gcm` crate).

| Property | Value |
|----------|-------|
| Algorithm | AES-256-GCM (AEAD) |
| Key length | 256 bits |
| Nonce length | 96 bits (12 bytes) |
| Nonce source | `OsRng` — fresh random nonce on every `commit` |
| Authentication tag | 128 bits (GCM default) |

The AEAD tag provides **integrity and authenticity** guarantees: any tampering with the ciphertext or nonce will cause decryption to fail deterministically. A failed decrypt is treated as an invalid password (the two cases are indistinguishable from the ciphertext alone).

## Key Lifecycle

```
create/unlock
    │
    ▼ Argon2id(password, salt) → key: [u8; 32]
    │                            derived in place into AesGcmCrypto.key
    │
    ├──► commit: key used in encrypt(), nonce refreshed each time
    │
    ├──► lock: reset() overwrites the key with 0x00 in place;
    │          entries are zeroized via the Zeroize derive on Entry
    │
    └──► process exit: ZeroizeOnDrop overwrites the key with 0x00
```

### Key Material Handling

- The raw key **never leaves the process** — it is not written to disk, logged, or transmitted.
- `AesGcmCrypto` derives `ZeroizeOnDrop` — the key is overwritten when the struct is dropped.
- `reset()` overwrites the key in place without dropping the struct. It runs on `lock` and when `unlock` fails, so no key (right or wrong) stays in memory. The key lives in a plain array rather than an `Option`, because `Option::take()` would copy it out and leave the original bytes behind.
- Entries derive `Zeroize` — on `lock()`, every entry is explicitly zeroized before the map is cleared.
- **Password history.** `update` moves the replaced password into the entry's history (inside the encrypted vault) instead of dropping it; past the last 10, the oldest is zeroized and dropped. Old passwords stay in the vault until then, or until the entry is removed.
- Passwords read from stdin via `rpassword` are held in `String` and zeroized (via `str.zeroize()`) immediately after use in the CLI layer.

## On-Disk Format

The format is defined byte by byte in `src/domain/format.rs`, with no serialization library in between. Formats v1 to v3 share this layout; v3 is written by this version:

| Bytes | Field |
|-------|-------|
| 6 | magic `VAULT\0` |
| 2 | format version, u16 little-endian |
| 1 | key derivation: `1` = Argon2id |
| 4 + 4 + 4 | Argon2 memory (KiB), passes, lanes, u32 little-endian |
| 16 | salt |
| 12 | AES-GCM nonce |
| rest | AES-256-GCM ciphertext, ending in the 16-byte tag |

The salt, nonce and parameters are stored in plaintext. This is standard and safe: none of them is secret.

- **The header is authenticated.** Everything before the nonce is passed to AES-GCM as associated data, so changing any header byte (version, cost, salt) makes decryption fail, exactly like a wrong password.
- **Costs are bounded before use.** The header can only be verified after the key is derived, so a file asking for more than 1 GiB of memory, 64 passes or 16 lanes is rejected as damaged before any derivation. A hostile file can't make unlock allocate gigabytes.
- **No size limit, no lying lengths.** The plaintext (entry count, then each entry's strings and timestamps; notes exist from v2 on, the password history from v3 on) is decoded by checking every length against the bytes actually present. A vault of any size reopens, and a corrupted length fails without reserving memory for it.
- **Version 0** (before the format had a version): salt, nonce, a u64 ciphertext length and the ciphertext, with no associated data. These files, like v1 and v2 files, are read and rewritten in the current format on unlock (see Key Derivation).
- A file from a **newer** version is refused with its version number, rather than misread.

### Nonce Reuse Prevention

A **fresh random nonce** is generated by `OsRng` on every `commit`. Nonce reuse under AES-GCM with the same key would be catastrophic (it leaks the authentication key and reveals plaintext XOR). Because the nonce is random and 96 bits wide, the probability of collision is negligible for any reasonable number of commits (birthday bound: ~2^48 commits for 1% collision probability).

## Backup & Integrity

Every commit, the storage adapter:

1. Takes `~/.vault/.lock` (`flock`), so commits from different sessions never interleave
2. Checks that the vault file is still the version this session last loaded or saved (SHA-256); if another session saved in the meantime, the commit is refused and nothing is written
3. Writes the current version to `<name>.bkp` and the new one to `<name>.vault`, each **atomically**: the data goes to a temporary file (mode `0600`), which is `fsync`ed and renamed over the target, then the directory is `fsync`ed

A crash or power loss at any point leaves each file either in its old state or its new one, never half-written. Since every save creates a fresh file, vaults written by older versions with looser permissions become `0600` on their next commit.

> **Note**: The SHA-256 here only detects changes made by another session. Vault contents are authenticated by the AES-GCM tag.

## Threat Model

### Protected Against

| Threat | Mitigation |
|--------|------------|
| Offline brute force on stolen vault file | Argon2id key derivation makes each attempt expensive |
| Ciphertext tampering | AES-GCM authentication tag — decryption fails on any modification |
| Header tampering (cost, salt, version) | The header is AES-GCM associated data; costs from a file are bounded before any key is derived |
| Secrets lingering in RAM after lock | `ZeroizeOnDrop` on key, `Zeroize` on entries, explicit zeroize on passwords |
| Vault file corruption on crash | Atomic replace: temporary file + `fsync` + `rename` + directory `fsync` |
| Lost updates between sessions | A commit is refused if another session saved since this one loaded the vault |
| Other local users reading vaults or exports | `~/.vault` is `0700`; vaults, backups and CSV exports are `0600`; an export never overwrites an existing file |
| Accidental vault overwrite | `create` and `rename` refuse a name that already belongs to a vault |

### Out of Scope / Limitations

| Threat | Status |
|--------|--------|
| Keylogger / clipboard snooping | Not mitigated — OS-level threat |
| Root/kernel-level memory access | Not mitigated — memory zeroization is best-effort in most OS environments |
| Side-channel attacks (timing, cache) | Not specifically hardened |
| Swap / hibernation leaking secrets | Not mitigated — use encrypted swap / disable hibernation |
| `.bkp` file left on disk | Backup is not deleted after a successful write — it holds the previous vault version. After `passwd` it is rewritten under the new password, so the old password no longer opens anything |
